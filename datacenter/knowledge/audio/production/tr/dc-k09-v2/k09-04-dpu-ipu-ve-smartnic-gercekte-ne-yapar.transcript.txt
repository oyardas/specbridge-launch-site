DPU konuşmalarında en büyük risk, güçlü bir network adaptörle gerçek infrastructure processing domain arasındaki farkın kaybolmasıdır. Bir NIC paket gönderir ve alır, SmartNIC programlı offload ekleyebilir. DPU veya IPU ise network, storage, security ve management servislerini host CPU’dan ayırarak ayrı bir execution ve trust domain oluşturmayı hedefleyebilir. Ancak ürün adları standart değildir, fonksiyonlar tek tek tanımlanmalıdır. Infrastructure offload’un temel amacı, host CPU’nun application workload’e daha fazla kaynak ayırılması olabilir. Virtual switch, overlay, routing, encryption, firewall, storage sanallaştırma veya telemetri DPU üzerinde çalıştığında host CPU core’ları bu işlerden kurtulabilir. Fakat offload ücretsiz değildir. DPU’nun kendi CPU’su, memory’si, accelerator engine’ı, firmware’i ve power budget’ı vardır. Aynı anda network, storage ve security servisi çalıştırılıyorsa hepsinin ortak kapasitesi test edilmelidir. İkinci değer isolation’dır. Cloud provider, infrastructure servislerini tenant operating system’inden ayrı bir processor üzerinde çalıştırabilir. Böylece tenant, host üzerindeki privileged software’den infrastructure control plane’i ayırmak mümkün olabilir. Fakat gerçek isolation, secure boot, firmware trust, access control ve management network tasarımına bağlıdır. DPU var demek, tek başına zero trust mimari kanıtı değildir. DPU failure domain olarak da değerlendirilmelidir. Bir hostun bütün network ve storage connectivity’si tek DPU üzerinden geçiyorsa, DPU arızası, CPU ve GPU sağlıklı olsa bile nodu servis dışı bırakabilir. İki port olması da redundancy kanıtı değildir. Portlar aynı device ve firmware domain’indedir. Gerekiyorsa dual DPU, alternate path veya cluster level evacuation modeli tasarlanmalıdır. AI cluster’larda DPU’nun rolü daha da belirgin olabilir. GPU’ya yüksek hızlı data taşınırken virtual networking, storage access, security ve tenant isolation, host CPU üzerinde önemli overhead yaratabilir. DPU bu işlerin bir kısmını offload ederek CPU ve GPU yutilizasyonunu arttırabilir. Fakat DPU scale-up GPU Fabric’in yerine geçmez. DPU’nun 400 veya 800 gigabit network portu olması, GPU peer interconnect’i veya cluster collective architecture’ı otomatik olarak çözmez. Storage acceleration da ayrı bir use case’dir. Remote NVMe, NVMe over fabrics, encryption, compression veya storage sanallaştırma DPU üzerinden işlenebilir. Bu durumda acceptance yalnız network packet testine dayanamaz. Network ve storage load aynı anda çalıştırılmalı. DPU, CPU, memory, queue, crypto ve storage engine’leri birlikte izlenmelidir. Management modeli önemlidir. DPU kendi operating system imajına, firmware’e, agent’lara ve orchestration tool’larına sahip olabilir. Bu platformu kim pad edecek? BMC team mi, network team mi, virtualization team mi? DPU reset edildiğinde host ne olur? Firmware update host reboot ister mi? Rollback nasıl yapılır? O sorular procurement sırasında kapanmalıdır. Vendor örnekleri kavramı anlamak için yararlıdır. Nvidia Bluefield, AMD Pensando ve Intel IPU, network, storage, security ve infrastructure offload alanlarında farklı implementationlar sunar. Fakat golden requirement vendor seçilerneyin yazmaz. Gereken packet rate, bandwidth, isolation, virtual function space’i, storage throughput, crypto, telemetry, management ve failover sonucu tanım var. DPU seçiminin ekonomik tarafı da vardır. Host CPU core tasarrufu, high yutilization ve security isolation değer yaratabilir. Ancak DPU CAPEX, power, software ve operations complexity ekler. DPU alındıysa otomatik TCO avantajı değildir. Kazanım representative workload altında ölçülmelidir. Golden sonuç nettir. DPU veya IPU bir aksesuar değil, infrastructure subsystem’dir. Data path, trust boundary, kapasite, failure behavior, management, ownership ve lifecycle ayrı ayrı modellenmelidir. DPU’nun platformdaki görevi açık değilse, bir OTU yalnız marka adı eklemek tasarım sayılmaz.
