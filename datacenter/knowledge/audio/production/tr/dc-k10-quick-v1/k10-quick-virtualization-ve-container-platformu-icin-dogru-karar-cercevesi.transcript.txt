Virtualization ve container projelerinde sık hata, teknoloji isimlerini aynı katmanda değerlendirmektir. VM bir işletim sistemi ve sanal donanım sınırı sunar. Container ise host kernel üzerinde process isolation ve packaging yaklaşımıdır. Hypervisor, container runtime ve orkestrator farklı görevler üstlenir. Kubernetes bir hypervisor değildir. OSI runtime da Kubernetes değildir. Bu ayrımlar doğru kurulmadan yapılan ürün karşılaştırması, gerçekte farklı problem sınıflarını aynı tabloda kıyaslamaya dönüşür. İlk karar, bu nedenle ürün değil, workload'un hangi isolation, lifecycle ve operasyon modeline ihtiyaç duyduğudur. İkinci karar, compute ve memory modelidir. vCPU, fiziksel core veya thread ile aynı şey değildir. Scheduler davranışı, CPU reservation, limit, overcommit, pinning, numa locality ve host contention birlikte değerlendirilmelidir. Memory tarafında configured memory, resident memory ve gerçek working set farklı kavramlardır. Overcommit kapasite verimliliği sağlayabilir, fakat performans garantisi değildir. Latency sensitive veya lisans bağımlı workload'larda CPU pinning, numa alignment ve predictable reservation, yoğun konsolidasyon ortamlarında ise güvenli overcommit oranı ve failure reserve daha kritik olabilir. Golden tasarım teorik host kapasitesini değil, yük altındaki davranışı kabul eder. Üçüncü karar, IO ve state zinciridir. Virtual switch, physical NIC, SR-IOV, passthrough, storage path, multipathing ve device locality performansı doğrudan etkiler. Passthrough veya SR-IOV daha düşük overhead sağlayabilir, ancak mobility, live migration ve failure recovery seçeneklerini sınırlayabilir. Benzer şekilde snapshot backup değildir. Live migration da HA veya DA değildir. Stateful workload için storage consistency, replication, restore ve application recovery ayrı ayrı test edilmelidir. Bir platformun özelliği bulunması, o özelliğin seçilen network, storage, driver ve firmware kombinasyonunda güvenilir şekilde çalıştığını kanıtlamaz. Dördüncü karar, container kontekst zinciridir. OCI image, OCI runtime ve OCI distribution birbirinden ayrı sözleşmelerdir. Image workload'un paketlenmiş file system ve metadata yapısını, runtime container'ın çalıştırılmasını, distribution ise image'in registry üzerinden taşınmasını tanımlar. Kubernetes tarafında CRI kublet ile container runtime entegrasyonu, CNI network bağlantısını, CSI storage entegrasyonunu tanımlar. Bunlar implementation değil, contracttır. Pod da container ile aynı şey değildir. Bir pod, bir veya daha fazla container için ortak scheduling ve network bağlamı sağlayabilir. Beşinci karar, availability ve security modelidir. GROP ve container isolation güçlü operasyon araçlarıdır. Fakat VM security boundary ile otomatik olarak eşdeğer kabul edilmemelidir. Runtime class seçimi, sandbox container yaklaşımı, setcomp, capabilities, image provenance, registry policy ve host hardening birlikte ele alınır. Availability tarafında VM restart HA, Kubernetes rescheduling, application clustering, ECUP ve DA farklı katmanlardır. Pod disruption budget planlı disruption yönetimine yardımcı olur. Donanım veya yazılım arızasına karşı tek başına application availability garantisi değildir. Recovery tasarımı, service dependency ve data consistency ile birlikte ölçülmelidir. Altıncı karar, hybrid modeldir. Bazı platformlarda VM'ler Kubernetes control plane altında yönetilebilir. Kubvert bunun bilinen örneklerinden biridir. Ancak Kubernetes üzerinde yönetilen bir VM hala VM'dir ve VM'in CPU, memory, storage, firmware ve guest operating system sorumlulukları ortadan kalkmaz. Benzer şekilde sandbox container daha güçlü isolation sağlayabilir, fakat performans, device access ve compatibility etkileri test edilmelidir. Hybrid yaklaşımın değeri bütün workload'ları aynı forma dönüştürmek değil, ortak policy ve operasyon katmanını doğru workload sınırlarıyla kullanabilmektir. Yedinci karar, lifecycle ve kapasite rezervidir. Cluster tasarımı yalnız normal gün kapasitesine göre yapılmamalıdır. Host failure, maintenance, rolling upgrade, node drain, image pull, storage recovery ve network degradation sırasında yeterli kaynak kalmalıdır. N artı bir ifadesi tek başına yeterli değildir. Hangi failure domain için ne kadar compute, memory, network ve storage reserve tutulduğu açık olmalıdır. Platform upgrade matrisi de hypervisor, guest tools, kernel, container runtime, Kubernetes, CNI, CSI, storage ve security komponent sürümlerini birlikte kapsamalıdır. Golden acceptance zincirini nettir. Workload ve isolation ihtiyacıyla sınıflandır. VM veya container execution modelini seç. CPU, vCPU, memory ve numa politikasını tanımla. Network, storage ve device path'ini haritala. Mobilite ile performans trade-off'unu doğrula. OCI, CRI, CNI ve CSI kontrakt zincirini doğrula. Security boundary ve image supply chain'ı test et. HA, backup ve DA sorumluluklarını ayır. Maintenance ve failure rezervi gerçek yük altında kanıtla. Support matiks, lifecycle, capex ve opex etkileriyle BOQ'yu freeze et. Doğru platform en fazla özelliği sunan değil, workload'u öngörülebilir performans, kontrollü isolation, test edilmiş recovery ve sürdürülebilir operasyon modeliyle çalıştıran platformdur.
